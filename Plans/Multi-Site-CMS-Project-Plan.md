# خطة مشروع Multi-Site CMS

## وثيقة الرؤية والمعمارية وخطة التنفيذ من البداية إلى الإطلاق

**حالة الوثيقة:** خطة ومواصفات فقط --- لا يوجد تنفيذ برمجي في هذه
المرحلة\
**الإصدار:** 1.0\
**التاريخ:** 3 نوفمبر 2026

------------------------------------------------------------------------

# 1. ملخص المشروع

إنشاء نظام مركزي خاص بمالك النظام لإدارة وإنشاء عدة مواقع إلكترونية من
لوحة تحكم واحدة. لكل موقع دومين مستقل، ومحتوى وهوية بصرية وصور وإعدادات
مستقلة، ويمكن اختيار قالب مختلف له في أي وقت.

النظام ليس منصة اشتراكات ولا خدمة متعددة المستخدمين. لا توجد حسابات
للشركات أو لوحات تحكم خاصة بالعملاء. توجد لوحة إدارة مركزية خاصة
بالمسؤول عن إنشاء المواقع وإدارتها.

الهدف النهائي هو إنشاء موقع جديد دون كتابة كود لكل مشروع: ندخل بياناته
وصوره ونختار قالباً ونعاينه ثم ننشره على الدومين الخاص به.

## المبادئ الأساسية

1.  فصل بيانات الموقع عن تصميم القالب.
2.  استقلال كل قالب في HTML وTailwind CSS وJavaScript.
3.  إضافة قالب جديد دون تعديل النظام الأساسي.
4.  تغيير قالب أي موقع في أي وقت دون فقد المحتوى.
5.  دعم Responsive حقيقي لجميع أحجام الشاشات.
6.  تشغيل النظام وقاعدة البيانات بالكامل باستخدام Docker.
7.  اعتماد آلية منظمة وآمنة لترحيل وتحديث قاعدة البيانات.
8.  توفير محتوى وصور افتراضية حتى يظهر الموقع مكتملاً قبل إدخال بيانات
    العميل.
9.  عدم إضافة أنظمة مستخدمين أو اشتراكات أو صلاحيات شركات.
10. إبقاء المشروع بسيطاً وقابلاً للصيانة والتوسع.

# 2. نطاق المشروع وما هو خارج النطاق

## داخل نطاق المشروع

-   لوحة تحكم إدارية مركزية واحدة.
-   إدارة عدة مواقع.
-   إدارة بيانات وهوية كل موقع.
-   إدارة الصفحات والأقسام والمحتوى.
-   إدارة الصور والملفات.
-   مكتبة قوالب مستقلة.
-   اكتشاف القوالب وإضافتها إلى المكتبة.
-   معاينة القوالب قبل اعتمادها.
-   تغيير قالب الموقع.
-   ربط عدة دومينات بالتطبيق المركزي.
-   تحديد الموقع المطلوب اعتماداً على الدومين.
-   نشر المواقع وإدارة حالتها.
-   بيانات وصور افتراضية قابلة للاستبدال.
-   Docker وMySQL.
-   نسخ احتياطي واستعادة.
-   ترحيلات قاعدة البيانات وإصداراتها.
-   اختبارات آلية وأمنية وأداء.

## خارج نطاق المشروع

-   تسجيل الشركات أو العملاء.
-   حساب مستقل لكل شركة.
-   لوحات تحكم للعملاء.
-   إدارة مستخدمين متعددين أو صلاحيات معقدة.
-   نظام اشتراكات أو فواتير أو مدفوعات.
-   متجر إلكتروني متكامل في الإصدار الأول.
-   محرر مرئي حر شبيه بأدوات بناء الصفحات بالسحب والإفلات في الإصدار
    الأول.

# 3. التقنيات واللغات المعتمدة

يجب أن تبقى الواجهة الأمامية والقوالب مبنية على التقنيات المطلوبة، مع
استخدام Backend واضح لإدارة البيانات وتقديمها.

  -----------------------------------------------------------------------
  الجزء                   التقنية المقترحة        الاستخدام
  ----------------------- ----------------------- -----------------------
  لغة القوالب             HTML5                   هيكل صفحات المواقع

  تنسيق القوالب           Tailwind CSS            تصميم متجاوب ومستقل لكل
                                                  قالب

  تفاعلات القوالب         JavaScript حديث         القوائم والتفاعلات
                                                  والواجهات

  لوحة الإدارة            HTML5 + Tailwind CSS +  واجهة الإدارة
                          JavaScript              

  Backend                 PHP 8.3+                API، منطق النظام،
                                                  التوجيه وإدارة البيانات

  قاعدة البيانات          MySQL 8.4 LTS           بيانات المواقع والمحتوى
                                                  والإعدادات

  الاتصال بقاعدة البيانات PDO                     استعلامات آمنة
                                                  وPrepared Statements

  خادم الويب              Nginx                   استقبال الطلبات
                                                  وتوجيهها

  الحاويات                Docker + Docker Compose تشغيل النظام وخدماته

  الاختبارات              PHPUnit + Playwright    اختبارات Backend
                                                  والواجهات والمتصفحات

  إدارة الاعتمادات        Composer + npm          مكتبات PHP وأدوات
                                                  CSS/JS

  التحكم بالإصدارات       Git                     حفظ مراحل التطوير
                                                  والتغييرات
  -----------------------------------------------------------------------

**ملاحظة:** Tailwind CSS يجب أن يُبنى إلى ملفات CSS نهائية عند النشر. لا
نعتمد على Tailwind CDN في الإنتاج.

## لماذا هذا الاختيار؟

-   PHP وMySQL مناسبان لتطبيق مركزي قابل للاستضافة.
-   HTML وTailwind وJavaScript يحققون شرط بناء القوالب دون فرض إطار
    واجهات ثقيل.
-   Docker يجعل بيئة التطوير والاختبار والإنتاج متقاربة.
-   Nginx مناسب لاستقبال دومينات متعددة وتوجيهها إلى التطبيق نفسه.
-   Playwright يساعد في اختبار العرض على أحجام شاشات ومتصفحات مختلفة.

لا نضيف React أو Vue أو Laravel أو مكتبات كبيرة في الإصدار الأول إلا إذا
ظهرت حاجة موثقة تبررها. يجب تثبيت إصدارات الأدوات في ملفات المشروع وعدم
استخدام إصدارات عائمة غير منضبطة.

# 4. التصور المعماري العام

يتكون النظام من أربعة أجزاء مستقلة:

1.  **Core CMS:** النظام الأساسي ولوحة الإدارة وواجهات API.
2.  **Website Data:** بيانات ومحتوى وإعدادات كل موقع.
3.  **Template Engine:** محرك تحميل القالب وربط البيانات به.
4.  **Publishing & Domain Routing:** توجيه الدومينات وعرض الموقع ونشره.

``` text
                  Internet / Visitors
                          |
                    DNS Records
                          |
                    Nginx / HTTPS
                          |
                   Domain Resolver
                          |
                 Website Configuration
                          |
             +------------+------------+
             |                         |
        Website Data              Template Engine
             |                         |
             +------------+------------+
                          |
                   Rendered Website
```

لوحة الإدارة تتصل بالنظام المركزي، ولا تظهر للزوار. مواقع الزوار لا تعرض
لوحة الإدارة ولا تسمح بتعديل المحتوى.

## قاعدة مهمة

القالب مسؤول عن العرض فقط. لا يجوز للقالب الاتصال بقاعدة البيانات أو
تنفيذ استعلامات SQL أو امتلاك منطق إدارة المحتوى. النظام الأساسي يجهز
البيانات، والقالب يعرضها.

# 5. طريقة عمل الدومينات

جميع الدومينات في الإصدار الأول تشير عبر DNS إلى الخادم نفسه. يستقبل
Nginx الطلب، ثم يقرأ التطبيق اسم المضيف من الطلب ويبحث عن الدومين
المسجل.

مثال توضيحي:

  الدومين         الموقع         القالب
  --------------- -------------- ---------------
  almeradi.ly     شركة المرادي   corporate-01
  asasalnour.ly   أساس النور     electrical-01
  novatech.ly     نوفا تك        technology-01

خطوات الطلب:

1.  يفتح الزائر `https://almeradi.ly`.
2.  يصل الطلب إلى Nginx.
3.  يمر الطلب إلى التطبيق المركزي.
4.  يتحقق التطبيق من اسم المضيف بعد تطبيعه والتحقق منه.
5.  يبحث عن الدومين في جدول الدومينات.
6.  يتأكد أن الموقع منشور ونشط.
7.  يجلب إعدادات ومحتوى الموقع.
8.  يحمّل القالب المعتمد لذلك الموقع.
9.  يعرض الصفحة المطلوبة.

## قواعد الدومينات

-   تخزين الدومين بصيغة موحدة lowercase ودون `www` في قيمة المقارنة.
-   دعم الدومين الأساسي والأسماء البديلة مثل `www`.
-   دعم أكثر من دومين للموقع الواحد عند الحاجة.
-   منع ربط الدومين نفسه بموقعين.
-   عدم الثقة في قيمة Host دون التحقق منها ومطابقتها بسجل معروف.
-   إظهار صفحة 404 أو صفحة موقع غير منشور عند عدم وجود تطابق.
-   توفير HTTPS وشهادة TLS لكل دومين.
-   عدم تمرير لوحة الإدارة عبر دومينات مواقع العملاء؛ تخصص لها وجهة
    إدارية منفصلة أو مسار محمي على نطاق الإدارة.

إعداد DNS وSSL جزء من متطلبات النشر والتشغيل، وليس مجرد كود داخل
التطبيق.

# 6. إدارة المواقع والمحتوى

## بيانات الموقع العامة

لكل موقع سجل مستقل يحتوي على:

-   الاسم التجاري.
-   الاسم المختصر أو slug.
-   الدومين الأساسي والدومينات البديلة.
-   وصف الموقع.
-   اللغة الافتراضية.
-   اتجاه العرض RTL أو LTR.
-   المنطقة الزمنية.
-   حالة الموقع: مسودة، منشور، متوقف.
-   القالب الحالي وإصداره.
-   بيانات SEO الافتراضية.

## الهوية البصرية

-   الشعار الأساسي.
-   شعار بديل للخلفيات الداكنة.
-   Favicon.
-   الألوان الأساسية والثانوية.
-   لون النصوص والخلفيات.
-   الخطوط.
-   بيانات التواصل.
-   روابط الشبكات الاجتماعية.

## الصفحات

يدعم النظام صفحات غير محدودة، مثل:

-   الرئيسية.
-   من نحن.
-   خدماتنا.
-   منتجاتنا.
-   مشاريعنا.
-   معرض الصور.
-   اتصل بنا.

كل صفحة تحتوي على slug وعنوان وحالة نشر وبيانات SEO وأقسام مرتبة.

## الأقسام والمحتوى

يجب توفير أنواع محتوى أساسية قابلة لإعادة الاستخدام:

-   Hero.
-   About.
-   Services.
-   Products.
-   Projects.
-   Statistics.
-   Features.
-   Partners.
-   Testimonials.
-   Team.
-   Gallery.
-   FAQ.
-   Contact.
-   Call To Action.

لا يشترط أن يستخدم كل قالب جميع الأقسام. يحدد كل قالب الأقسام التي
يستطيع عرضها، ويمكن أن يضيف أنواعاً خاصة به وفق مواصفات واضحة.

# 7. معمارية القوالب

هذه من أهم أجزاء المشروع، ويجب تصميمها قبل بناء القوالب الفعلية.

## استقلال القوالب

كل قالب مجلد مستقل ويحتوي على:

-   ملف تعريف `template.json`.
-   صفحات HTML.
-   ملفات CSS المبنية من Tailwind.
-   ملفات JavaScript.
-   صور وأيقونات القالب.
-   مكونات داخلية عند الحاجة.
-   صورة معاينة.
-   ملف توثيق يشرح الأقسام والحقول المدعومة.

مثال هيكلي:

``` text
templates/
  corporate-01/
    template.json
    preview.webp
    pages/
      home.html
      about.html
      services.html
      contact.html
    assets/
      css/
      js/
      images/
    components/
    README.md

  electrical-01/
    template.json
    preview.webp
    pages/
    assets/
    components/
    README.md
```

## ملف تعريف القالب

يحتوي على الأقل على:

-   معرف ثابت وفريد.
-   اسم القالب.
-   الإصدار.
-   الوصف والتصنيف.
-   صورة المعاينة.
-   الصفحات المدعومة.
-   أنواع الأقسام المدعومة.
-   مفاتيح البيانات المطلوبة والاختيارية.
-   الحد الأدنى لإصدار النظام المتوافق.

يجب التحقق من ملف التعريف والملفات المطلوبة قبل إظهار القالب باعتباره
صالحاً للاستخدام.

## اكتشاف القوالب

عند تشغيل النظام أو تحديث مكتبة القوالب، يفحص النظام مجلد `templates`
ويكتشف القوالب التي تحتوي على ملف تعريف صالح. لا ينبغي تنفيذ أي ملف
JavaScript أو PHP من القالب أثناء عملية الاكتشاف.

## اتفاقية البيانات بين النظام والقالب

يقدم النظام للقالب كائن بيانات موحداً يحتوي على:

-   `site`: بيانات الموقع العامة.
-   `branding`: الشعار والألوان والخطوط.
-   `contact`: معلومات التواصل.
-   `navigation`: روابط التنقل.
-   `page`: بيانات الصفحة الحالية.
-   `sections`: أقسام الصفحة وترتيبها ومحتواها.
-   `media`: مسارات الصور والملفات.
-   `seo`: العنوان والوصف والصورة وبيانات المشاركة.
-   `locale`: اللغة والاتجاه.

القالب لا يعتمد على أسماء جداول قاعدة البيانات؛ يعتمد على عقد بيانات
موثق ومستقر.

## القوالب الخاصة

يمكن للقالب تعريف حقول إضافية خاصة به، لكن يجب أن تكون معرفة في ملف
تعريف القالب، وأن تخزن ضمن إعدادات أو محتوى منظم خاص بالقالب. لا يسمح
بإضافة أعمدة SQL جديدة لكل قالب.

# 8. تغيير القالب في أي وقت

يجب أن تكون عملية تغيير القالب آمنة وقابلة للتراجع.

عند تغيير قالب موقع:

1.  يختار المسؤول القالب الجديد.
2.  يفحص النظام توافق القالب مع إصدار النظام.
3.  يعرض معاينة باستخدام بيانات الموقع الحقيقية.
4.  يحدد الحقول أو الأقسام غير المدعومة في القالب الجديد.
5.  لا يحذف النظام أي محتوى لمجرد أن القالب الجديد لا يعرضه.
6.  ينشئ النظام نسخة من إعدادات القالب الحالي قبل التغيير.
7.  يعتمد القالب الجديد بعد موافقة المسؤول.
8.  يمكن الرجوع إلى القالب السابق.

**قاعدة إلزامية:** المحتوى والصفحات والصور والبيانات العامة ملك للموقع
وليست ملكاً للقالب. تغيير القالب لا يحذفها ولا يعيد إنشاءها.

قد تختلف طريقة عرض قسم من قالب إلى آخر. إذا لم يدعم القالب الجديد نوع
قسم معيناً، يحتفظ النظام ببياناته ويعرض تنبيهاً في المعاينة بدلاً من حذفها.

# 9. القيم الافتراضية والصور التجريبية

يجب ألا يظهر الموقع فارغاً أو مكسوراً عند إنشائه لأول مرة.

عند إنشاء موقع جديد، ينشئ النظام بيانات ابتدائية افتراضية قابلة للتعديل،
مثل:

-   اسم تجريبي للشركة.
-   وصف قصير مناسب للنشاط.
-   عنوان رئيسي ووصف فرعي.
-   بيانات تواصل تجريبية واضحة.
-   خدمات أو منتجات نموذجية.
-   روابط تنقل افتراضية.
-   إعدادات ألوان وخطوط افتراضية.
-   صور مناسبة لكل قسم.
-   شعار تجريبي وFavicon افتراضيان.
-   صور بديلة عند غياب صورة معينة.

## مكتبة الصور الافتراضية

تنظم حسب الاستخدام:

``` text
default-media/
  logos/
  hero/
  about/
  services/
  products/
  projects/
  gallery/
  team/
  placeholders/
```

## قواعد الصور الافتراضية

-   استخدام صور محلية مرخصة أو صور أنشئت خصيصاً للمشروع.
-   عدم الاعتماد على روابط صور خارجية قد تتوقف.
-   توفير أحجام مناسبة ونسب أبعاد موثقة.
-   استخدام WebP أو AVIF عند دعم بيئة العرض، مع بدائل مناسبة.
-   عدم تمديد الصور أو تشويهها.
-   توفير صورة بديلة عند فشل التحميل.
-   وضع علامة واضحة في لوحة الإدارة بأن المحتوى تجريبي أو افتراضي.
-   عدم نشر بيانات تجريبية على أنها بيانات حقيقية دون مراجعة المسؤول.
-   تمكين المسؤول من استبدال كل صورة ونص وشعار بسهولة.

يجب أن يكون هناك زر أو إجراء واضح لإعادة تعبئة بيانات العرض الافتراضية
عند إنشاء موقع جديد، لا عند كل زيارة للموقع.

# 10. التصميم المتجاوب Responsive

Responsive شرط قبول إلزامي لكل قالب، وليس تحسيناً اختيارياً.

## نطاقات الاختبار

  الفئة           عرض الشاشة المستهدف
  ------------- ---------------------
  هاتف صغير                     320px
  هاتف                          375px
  هاتف كبير                     430px
  جهاز لوحي                     768px
  حاسوب محمول          1024px و1366px
  شاشة مكتبية                  1440px
  شاشة كبيرة                   1920px

يجب أن يدعم كل قالب:

-   Mobile First.
-   قوائم مناسبة للمس على الهاتف.
-   صوراً مرنة لا تتجاوز الحاويات.
-   خطوطاً ومسافات تتكيف مع الشاشة.
-   عدم وجود تمرير أفقي غير مقصود.
-   جداول وبطاقات مناسبة للشاشات الصغيرة.
-   أزراراً ومساحات لمس مناسبة.
-   RTL وLTR.
-   حالات تحميل وفشل الصور.
-   تبايناً مناسباً وإمكانية استخدام لوحة المفاتيح.

## اختبار القوالب

يستخدم Playwright لاختبار الصفحات الأساسية على أحجام العرض المحددة،
والتحقق من:

-   عدم وجود Horizontal Overflow.
-   ظهور القائمة وعملها.
-   عدم تداخل النصوص والصور.
-   عدم وجود أخطاء JavaScript.
-   تحميل الخطوط والأصول.
-   عمل الروابط والنماذج.

# 12. النشر والتصدير

يجب التمييز بين تشغيل الموقع من النظام المركزي وبين تصديره كملفات
مستقلة.

## المسار الأساسي في الإصدار الأول

تشغيل جميع المواقع من التطبيق المركزي، بحيث:

-   الدومينات تشير إلى الخادم نفسه.
-   التطبيق يحدد الموقع حسب الدومين.
-   كل موقع يستخدم بياناته وقالباً مستقلاً.
-   تحديث المحتوى يظهر في الموقع بعد النشر.
-   لا نحتاج إلى إنشاء تطبيق مستقل لكل موقع.

## التصدير المستقل

يُدرس كميزة لاحقة بعد استقرار محرك القوالب. يمكن أن ينتج ملفات
HTML/CSS/JS وصوراً مستقلة لموقع لا يحتاج إلى وظائف ديناميكية.

يجب عدم الادعاء بأن كل موقع قابل للتصدير بصورة صحيحة قبل التأكد من أن
القالب لا يعتمد على وظائف Backend وقت التشغيل. لذلك يصمم النظام من
البداية مع فصل واضح بين البيانات والعرض، لكن لا نؤخر الإصدار الأول ببناء
نظام تصدير كامل.

# 13. Docker وبيئة التشغيل

يعمل النظام وقاعدة البيانات داخل Docker باستخدام Docker Compose.

## الخدمات المقترحة

``` text
docker-compose.yml
  app
    PHP application

  web
    Nginx

  db
    MySQL 8.4 LTS

  db-backup (optional profile)
    Scheduled backup task
```

يمكن أن تتم إضافة خدمة أدوات البناء عند الحاجة، لكن لا نضيف خدمات دائمة
دون مبرر.

## التخزين الدائم

-   تخزين قاعدة البيانات في Docker Named Volume.
-   تخزين الصور والملفات المرفوعة في Volume دائم أو مسار تخزين دائم.
-   عدم حفظ بيانات المستخدمين أو الصور المهمة داخل طبقة الحاوية المؤقتة.
-   عدم تضمين كلمات المرور أو مفاتيح الإنتاج في Git.
-   استخدام ملف `.env` محلي، وملف `.env.example` يوضح المتغيرات المطلوبة
    دون أسرار.

## ملفات Docker المتوقعة

-   `Dockerfile`
-   `docker-compose.yml`
-   `docker-compose.override.yml` للتطوير عند الحاجة
-   `docker/nginx/`
-   `docker/php/`
-   `.dockerignore`
-   `.env.example`

## متطلبات Docker

-   تثبيت إصدارات صور الحاويات وعدم استخدام `latest` في الإنتاج.
-   فحص صحة MySQL باستخدام healthcheck.
-   جعل التطبيق ينتظر جاهزية قاعدة البيانات.
-   عدم نشر منفذ MySQL للعامة في الإنتاج.
-   تشغيل PHP وNginx بأقل صلاحيات ممكنة.
-   فصل إعدادات التطوير عن الإنتاج.
-   توفير أوامر موثقة للتشغيل والإيقاف وإعادة البناء والنسخ الاحتياطي.

# 14. آلية تحديث قاعدة البيانات Database Migrations

هذه نقطة أساسية في المشروع. لا نعتمد على إنشاء الجداول تلقائياً عند كل
تشغيل، ولا نعدل قاعدة الإنتاج يدوياً دون ترحيل موثق.

## الآلية المقترحة

اعتماد نظام migrations مرتب زمنياً، باستخدام PHP migrations أو أداة
موثوقة متوافقة مع PHP وMySQL. يجب اختيار أداة واحدة وتثبيت قرارها قبل
التنفيذ.

كل migration تكون ملفاً مستقلاً باسم زمني واضح، مثال:

``` text
database/
  migrations/
    202611030001_create_websites_table.php
    202611030002_create_domains_table.php
    202611030003_create_templates_table.php
    202611030004_create_pages_table.php
```

## جدول تتبع الترحيلات

يحتوي النظام على جدول مثل `schema_migrations` يسجل:

-   اسم الترحيل.
-   رقم الإصدار أو الترتيب.
-   وقت التنفيذ.
-   نتيجة التنفيذ أو بيانات التتبع الضرورية.

عند تشغيل أمر الترحيل:

1.  يتصل النظام بقاعدة البيانات.
2.  يقرأ الترحيلات المسجلة.
3.  يحدد الملفات التي لم تنفذ.
4.  ينفذ الترحيلات بالترتيب.
5.  يسجل نجاح كل ترحيل.
6.  يتوقف بوضوح عند الخطأ، ولا يعتبر الترحيل الفاشل ناجحاً.

## أوامر تشغيل مقترحة

``` bash
docker compose exec app php bin/console db:migrate
docker compose exec app php bin/console db:migrate:status
docker compose exec app php bin/console db:seed
```

هذه أسماء أوامر مقترحة وليست أوامر منفذة بعد؛ تثبت الأسماء النهائية عند
تصميم CLI.

## قواعد تحديث قاعدة البيانات

-   كل تغيير في بنية قاعدة البيانات يجب أن يكون عبر Migration.
-   يمنع تعديل قاعدة الإنتاج يدوياً كطريقة تحديث اعتيادية.
-   لا تنفذ migrations تلقائياً في كل طلب HTTP.
-   لا تنفذ migrations تلقائياً عند تشغيل كل نسخة من التطبيق في الإنتاج
    دون خطوة نشر مضبوطة.
-   خذ نسخة احتياطية قبل التحديثات المؤثرة.
-   اختبر الترحيلات على نسخة اختبار من قاعدة البيانات.
-   يجب أن تكون الترحيلات قابلة للتتبع.
-   لا تحذف أعمدة أو بيانات مباشرة دون خطة انتقال وحفظ بيانات.
-   استخدم أسلوب Expand/Contract للتغييرات الكبيرة: إضافة بنية جديدة،
    نقل البيانات والتحقق منها، ثم إزالة القديمة في إصدار لاحق.
-   لا تفترض أن كل عمليات DDL في MySQL قابلة للتراجع Transactionally؛
    صمم الترحيلات مع مراعاة ذلك.
-   وفر خطة استعادة من النسخة الاحتياطية عند فشل التحديث.

## Seeders

تستخدم Seeders لإضافة البيانات الابتدائية مثل:

-   أنواع الأقسام.
-   إعدادات النظام الافتراضية.
-   بيانات العرض التجريبية.
-   بيانات القوالب الأولية.

يجب أن تكون Seeders قابلة لإعادة التشغيل دون تكرار السجلات أو إفساد
بيانات المواقع الحقيقية. لا يجوز أن تستبدل محتوى المواقع الموجودة عند كل
تشغيل.

# 15. تصور قاعدة البيانات

هذا تصور أولي للجداول، وليس مخططاً نهائياً قبل مرحلة التصميم التفصيلي.

  الجدول                      المسؤولية
  --------------------------- ---------------------------------
  websites                    بيانات كل موقع وحالته
  domains                     الدومينات الأساسية والبديلة
  templates                   القوالب المسجلة وإصداراتها
  website_template_settings   إعدادات القالب لكل موقع
  pages                       صفحات المواقع
  sections                    أقسام الصفحات وترتيبها ومحتواها
  media                       بيانات الصور والملفات
  navigation_menus            قوائم التنقل
  navigation_items            عناصر القوائم
  website_settings            إعدادات الموقع العامة
  schema_migrations           سجل تحديثات بنية قاعدة البيانات

## قواعد تصميم البيانات

-   استخدام مفاتيح أساسية وعلاقات واضحة.
-   `domain` فريد على مستوى النظام بالكامل، ولا يمكن ربط الدومين نفسه بأكثر من موقع.
-   `slug` فريد داخل الموقع نفسه فقط، باستخدام قيد مركب على معرّف الموقع والـ slug.
-   استخدام فهارس للأعمدة التي يكثر البحث بها.
-   تخزين التواريخ بتنسيق واضح ومعتمد.
-   تخزين المحتوى المرن في JSON عند الحاجة، مع عدم تحويل كل البيانات إلى
    JSON بلا سبب.
-   فصل بيانات الموقع المشتركة عن إعدادات القالب الخاصة.
-   عدم إنشاء جدول جديد لكل موقع أو لكل قالب.
-   وضع قيود لحماية سلامة العلاقات.
-   تحديد سياسة الحذف: حذف منطقي أو أرشفة عند الحاجة لتجنب فقد البيانات
    بالخطأ.

# 16. الأمان

الأمان جزء من التصميم الأولي، وليس مرحلة تجميلية.

-   حماية لوحة الإدارة بتسجيل دخول إداري قوي.
-   لا توجد حسابات للشركات أو المستخدمين الخارجيين.
-   تخزين كلمات المرور باستخدام password hashing الآمن في PHP.
-   حماية جلسات الإدارة وCookies.
-   استخدام CSRF protection للنماذج والطلبات التي تغير البيانات.
-   استخدام PDO Prepared Statements.
-   التحقق من المدخلات وتنقية المخرجات لمنع XSS.
-   التحقق من نوع وحجم الصور والملفات المرفوعة ومحتواها.
-   منع رفع ملفات تنفيذية إلى مجلدات عامة.
-   حماية مسارات القوالب ومنع Path Traversal.
-   عدم تنفيذ ملفات PHP داخل مجلدات القوالب أو الرفع.
-   عدم السماح للقالب بتحديد مسار ملف عشوائي.
-   ضبط Host allowlist أو التحقق من الدومينات المسجلة.
-   استخدام HTTPS.
-   حماية ملفات `.env` والنسخ الاحتياطية من الوصول العام.
-   تحديث صور Docker والاعتمادات بشكل مدروس.
-   تسجيل الأخطاء دون كشف أسرار أو تفاصيل داخلية للزوار.

# 19. خطة التنفيذ من البداية إلى النهاية

لن يتم تنفيذ جميع المراحل دفعة واحدة. كل مرحلة لها نتيجة قابلة للفحص
ومعايير قبول. لا ننتقل إلى المرحلة التالية قبل اجتياز المرحلة الحالية.

## المرحلة التمهيدية: تثبيت المتطلبات والتصميم المعماري

**المهام:** - تثبيت نطاق المشروع وما هو خارج النطاق. - اعتماد اللغات
والتقنيات. - اعتماد أسلوب تشغيل المواقع عبر الدومينات. - تحديد عقد
البيانات بين Core والقوالب. - تحديد سياسة تخزين الصور والملفات. - اعتماد
استراتيجية migrations والنسخ الاحتياطي. - توثيق قرارات المعمارية.

**المخرجات:** - وثيقة متطلبات. - مخطط معماري. - قرارات تقنية موثقة.

**معيار القبول:** لا توجد قرارات أساسية متعارضة أو أجزاء غير محددة تؤثر
على قاعدة البيانات أو القوالب.

## المرحلة 1: تصميم قاعدة البيانات

**المهام:** - تحديد الكيانات والعلاقات. - تحديد أنواع الحقول والقيود
والفهارس، مع جعل `domain` فريداً على مستوى النظام ومنع ربطه بأكثر من
موقع، وجعل `slug` فريداً داخل الموقع نفسه فقط. - تحديد كيفية تخزين الأقسام والحقول المرنة. - تحديد علاقة
الدومينات بالمواقع. - تحديد علاقة المواقع بالقوالب وإصداراتها. - تصميم
جدول migrations. - تحديد Seeders الافتراضية.

**المخرجات:** - ERD. - قاموس بيانات. - قائمة migrations مرتبة.

**معيار القبول:** يمكن تمثيل عدة مواقع ودومينات وصفحات وأقسام وقوالب دون
تكرار أو ربط المحتوى بتصميم واحد.

**اختبارات المرحلة:** مراجعة ERD وقاموس البيانات والتحقق من حالات تكرار
الدومين وربطه بموقع ثانٍ وتكرار slug داخل الموقع وخارجه.

## المرحلة 2: تأسيس Docker وبيئة التطوير

**المهام:** - إعداد Dockerfile. - إعداد Docker Compose. - إعداد PHP
وNginx وMySQL. - إعداد Volumes دائمة. - إعداد متغيرات البيئة. - إعداد
Healthchecks. - توثيق أوامر التشغيل والإيقاف والسجلات.

**المخرجات:** بيئة تطوير تعمل من خلال Docker.

**اختبارات المرحلة:** تشغيل الخدمات وإيقافها وإعادة تشغيلها والتحقق من
Healthchecks وVolumes واستمرارية البيانات.

**معيار القبول:** يستطيع المطور تشغيل التطبيق وقاعدة البيانات وإيقافهما
وإعادة تشغيلهما دون فقد البيانات الدائمة.

## المرحلة 3: تنفيذ Migrations وإنشاء الجداول الأساسية

**المهام:** - تنفيذ نظام تتبع migrations. - إنشاء الجداول الأساسية
والقيود والفهارس. - تنفيذ قيد فريد عام للدومين وقيد فريد مركب لـ
`website_id` و`slug`. - تنفيذ Seeders آمنة قابلة لإعادة التشغيل. - إعداد
أوامر status وmigrate. - إعداد النسخ الاحتياطي والاستعادة.

**المخرجات:** قاعدة بيانات يمكن إنشاؤها وتحديثها بطريقة موثقة.

**معيار القبول:** يمكن إنشاء قاعدة جديدة من الصفر وتحديث قاعدة موجودة دون
فقد بياناتها، وتُرفض الدومينات المكررة وslugs المكررة داخل الموقع نفسه.

**اختبارات المرحلة:** تشغيل migrations على قاعدة فارغة وقاعدة تحتوي بيانات،
والتحقق من القيود والفهارس وSeeders والاستعادة.

## المرحلة 4: بناء Core Backend

**المهام:** - إعداد نقطة دخول التطبيق. - إعداد Routing. - إعداد الاتصال
الآمن بقاعدة البيانات. - إعداد طبقات Controllers وServices وRepositories.
- إعداد Validation ومعالجة الأخطاء. - إعداد Domain Resolver. - إعداد API
الداخلية للوحة الإدارة. - إعداد تسجيل الدخول الإداري الوحيد.

**المخرجات:** Backend منظم وقابل للاختبار.

**معيار القبول:** يستطيع النظام تحديد الموقع الصحيح من الدومين وإرجاع
بياناته دون خلط بين المواقع.

**اختبارات المرحلة:** اختبارات وحدات وتكامل للـ Routing وDomain Resolver
والتحقق من المدخلات والمصادقة وعزل بيانات المواقع.

## المرحلة 5: لوحة الإدارة الأساسية

**المهام:** - تصميم واجهة إدارية بسيطة وواضحة. - Dashboard. - قائمة
المواقع. - إضافة وتعديل وأرشفة موقع. - إدارة الدومينات. - إدارة بيانات
الشركة والهوية. - إدارة الإعدادات العامة. - حالات الحفظ والنجاح والخطأ.

**المخرجات:** لوحة إدارة مركزية لإدارة المواقع.

**معيار القبول:** يمكن إنشاء عدة مواقع وتعديل بيانات كل موقع دون تداخل.

**اختبارات المرحلة:** إنشاء موقعين وتعديلهما وإدارة دوميناتهما والتحقق من العزل ورسائل النجاح والخطأ.

## المرحلة 6: إدارة المحتوى والوسائط

**المهام:** - إدارة الصفحات. - إدارة الأقسام وترتيبها. - إدارة النصوص
والعناوين والأزرار. - إدارة الخدمات والمنتجات والمشاريع. - رفع الصور
والملفات. - مكتبة الوسائط. - ربط الصور بالمحتوى. - إدخال البيانات
الافتراضية. - استبدال المحتوى التجريبي بسهولة.

**المخرجات:** محتوى متكامل لكل موقع.

**معيار القبول:** يمكن تجهيز موقع كامل من لوحة الإدارة دون تحرير HTML
يدوياً.

**اختبارات المرحلة:** إنشاء الصفحات والأقسام ورفع واستبدال الوسائط والتحقق من بقاء المحتوى الافتراضي معزولاً لكل موقع.

## المرحلة 7: بناء Template Engine

**المهام:** - اعتماد بنية مجلد القالب. - تعريف Schema لملف
`template.json`. - اكتشاف القوالب والتحقق منها. - تعريف عقد البيانات
الموحد. - تحميل الصفحات والأصول. - ربط بيانات الصفحات والأقسام. - دعم
الأقسام الاختيارية والخاصة بالقالب. - معالجة القالب غير الصالح أو
المفقود.

**المخرجات:** محرك قوالب مستقل عن لوحة الإدارة والمحتوى.

**معيار القبول:** إضافة قالب تجريبي جديد إلى مجلد القوالب تجعله يظهر في
المكتبة دون تعديل Core.

**اختبارات المرحلة:** اكتشاف قالب صالح ورفض ملف تعريف غير صالح والتحقق من عقد البيانات ومعالجة القالب المفقود.

## المرحلة 8: معاينة القوالب وتغييرها

**المهام:** - عرض مكتبة القوالب. - عرض صورة ومعاينة لكل قالب. - معاينة
باستخدام بيانات الموقع الفعلية. - عرض Desktop وTablet وMobile. - فحص
توافق الأقسام. - حفظ إعدادات القالب السابقة. - تطبيق القالب الجديد. -
توفير الرجوع إلى القالب السابق.

**المخرجات:** تجربة آمنة لاختيار وتغيير القالب.

**معيار القبول:** تغيير القالب لا يحذف المحتوى أو الصور أو الصفحات،
ويمكن التراجع عنه.

**اختبارات المرحلة:** معاينة القالب على المقاسات المطلوبة وفحص التوافق والتغيير والتراجع مع التأكد من بقاء المحتوى.

## المرحلة 9: إنشاء القوالب الأولى

**القوالب الأولية:** 1. Corporate: للشركات والمؤسسات. 2.
Industrial/Electrical: للمصانع والمواد الكهربائية. 3. Technology: لشركات
التقنية والاتصالات.

**المهام لكل قالب:** - تصميم بصري مستقل. - صفحات رئيسية وداخلية. -
مكونات خاصة بالقالب. - Tailwind CSS مستقل مبني للإنتاج. - JavaScript خاص
بالقالب. - ربط البيانات بالعقد الموحد. - Responsive. - RTL وLTR. - SEO
وAccessibility. - صورة معاينة وتوثيق.

**معيار القبول:** القوالب الثلاثة مختلفة فعلياً في التصميم، وتعرض
البيانات نفسها بطرق مناسبة لكل مجال.

**اختبارات المرحلة:** اختبار كل قالب على RTL وLTR ومقاسات Responsive والتحقق من SEO وAccessibility.

## المرحلة 10: النشر وربط الدومينات

**المهام:** - إعداد Nginx لاستقبال الدومينات. - توجيه جميع الدومينات إلى
التطبيق. - إعداد DNS. - إعداد HTTPS وSSL. - دعم www والدومين الأساسي. -
إعداد صفحات 404 والمواقع غير النشطة. - إعداد التخزين المؤقت وإبطال Cache
بعد النشر.

**المخرجات:** مواقع حقيقية تعمل على دومينات مستقلة.

**معيار القبول:** فتح كل دومين يعرض الموقع الصحيح وقالبَه ومحتواه، دون
تداخل.

**اختبارات المرحلة:** اختبار DNS وHost normalization وwww وHTTPS وصفحات 404 والمواقع غير النشطة والتخزين المؤقت.

## المرحلة 11: اختبارات التكامل الشاملة End-to-End

هذه المرحلة مخصصة لاختبارات النظام المتكامل End-to-End فقط، بعد اجتياز
اختبارات كل مرحلة السابقة. تغطي المسار الكامل من المتصفح وDNS وNginx إلى
التطبيق وقاعدة البيانات والقالب والموقع المنشور.

**الاختبارات:** - إنشاء موقع من لوحة الإدارة. - ربط دومين والتحقق من منع
تكراره. - إدخال المحتوى والوسائط. - اختيار قالب ومعاينته وتغييره
والتراجع عنه. - نشر الموقع وزيارته عبر HTTP وHTTPS. - التحقق من العزل
الكامل بين موقعين. - اختبار المسارات الحرجة على 320px و768px و1366px
و1920px. - التحقق من عدم تسرب بيانات أو أخطاء تمنع النشر.

**معيار القبول:** نجاح سيناريوهات End-to-End الحرجة كاملة، دون استخدام
هذه المرحلة بديلاً عن اختبارات المراحل السابقة.

## المرحلة 12: الإطلاق والتوثيق والصيانة

**المهام:** - إعداد Docker للإنتاج. - فتح المنفذ 80 للاتصال HTTP. - فتح
المنفذ 443 للاتصال HTTPS. - تفعيل شهادات SSL/TLS لجميع الدومينات. - إعداد
التجديد التلقائي للشهادات. - تحويل HTTP إلى HTTPS. - إبقاء منفذ MySQL
داخلياً وعدم تعريضه للإنترنت. - إعداد الأسرار ومتغيرات البيئة. -
إعداد النسخ الاحتياطي الدوري. - تجربة استعادة النسخة الاحتياطية. - توثيق
نشر دومين جديد. - توثيق إضافة قالب جديد. - توثيق تحديث قاعدة البيانات. -
توثيق تحديث التطبيق. - إعداد مراقبة السجلات والأخطاء. - وضع خطة تحديث
وصيانة دورية.

**المخرجات:** نظام جاهز للاستخدام الفعلي والصيانة والتوسع.

**اختبارات المرحلة:** فحص المنافذ وقواعد الجدار الناري، والتحقق من شهادات
SSL/TLS وتجديدها وتحويل HTTP إلى HTTPS، والتأكد من عدم الوصول إلى MySQL من
الإنترنت، ثم اختبار النسخ الاحتياطي والاستعادة.

# 23. قرارات يجب تثبيتها قبل بدء التنفيذ

هذه الخطة تعتمد القرارات التالية مبدئياً:

1.  لوحة إدارة واحدة خاصة بمالك النظام.
2.  لا توجد حسابات عملاء أو إدارة مستخدمين متعددة.
3.  PHP وMySQL هما Backend وقاعدة البيانات.
4.  HTML5 وTailwind CSS وJavaScript هي تقنيات القوالب والواجهة.
5.  جميع الخدمات تعمل داخل Docker.
6.  MySQL تعمل داخل Docker مع Volume دائم.
7.  تشغيل المواقع عبر نظام مركزي ودومينات متعددة في الإصدار الأول.
8.  المحتوى منفصل عن القوالب.
9.  القوالب مستقلة وقابلة للاكتشاف.
10. تغيير القالب لا يحذف البيانات.
11. البيانات والصور الافتراضية متوفرة لكل موقع جديد.
12. تحديث قاعدة البيانات يتم من خلال Migrations صريحة وموثقة.
13. نبدأ بثلاثة قوالب مختلفة.
14. التصدير إلى مواقع ثابتة مستقلة ميزة لاحقة بعد استقرار النظام.

أي تغيير على هذه القرارات يجب توثيقه قبل تنفيذه إذا كان يؤثر في
المعمارية أو قاعدة البيانات.

# 24. طريقة إدارة تنفيذ المشروع

-   هذه الوثيقة هي مرجع المشروع الأساسي.
-   لا يبدأ التنفيذ قبل مراجعة واعتماد المرحلة صفر.
-   تنفذ مرحلة واحدة في كل مرة.
-   قبل كل مرحلة تحدد الملفات المتأثرة والمخرجات ومعايير القبول.
-   لا يتم إجراء Refactoring خارج نطاق المرحلة دون سبب موثق.
-   لا تضاف مكتبات أو خدمات جديدة لمجرد التفضيل.
-   لا يتم الانتقال للمرحلة التالية قبل تشغيل الاختبارات المطلوبة.
-   تحفظ التغييرات في Git على مراحل صغيرة واضحة.
-   يتم تحديث هذه الوثيقة عند تغيير قرار معماري.
-   لا تعتبر المهمة مكتملة بمجرد كتابة الكود؛ يجب اختبار النتيجة
    وتوثيقها.

## النتيجة المستهدفة

نظام مركزي قوي وسهل الاستخدام، يسمح بإنشاء مواقع متعددة وإدارتها من مكان
واحد، مع قوالب مستقلة ومتنوعة وقابلة للإضافة والتبديل، ومحتوى افتراضي
يجعل كل موقع واضحاً منذ البداية، وتشغيل موحد عبر Docker وMySQL، وتحديثات
قاعدة بيانات منظمة وآمنة.

**نهاية وثيقة الخطة --- لا تتضمن هذه الوثيقة أي تنفيذ برمجي.**
